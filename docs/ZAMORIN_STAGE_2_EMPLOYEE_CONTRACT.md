# Zamorin Cafe ERP — Stage 2.2 Employee Schema and Read-Contract Design

## 1. Design identity

- **Stage**: Stage 2.2 — Employee schema and response-contract design
- **Starting checkpoint**: `64ead22`
- **Architecture**: Vercel frontend → Render Express API → MongoDB Atlas through Mongoose
- **Design decision**: `STAGE_2_2_DESIGN_COMPLETE`
- **Scope**: Employee search and read-only full employee profile
- **Permanent identity**: The existing `User` document and immutable `userId`

No second Employee collection or duplicate identity will be created.

## 2. Confirmed current mutation contract

The existing `createUser` endpoint accepts the required identity and access fields: name, email, password, role, phone, preferred name, preferred language and café assignments.

The existing general `updateUser` endpoint permits name, preferred name, phone, preferred language, email and governed café assignments. Stage 1 protects identity, role, Primary Master metadata, histories, security fields, status and version fields.

Stage 2 read implementation will not weaken those protections. New employee-profile fields will not be silently accepted by the existing general update endpoint during the first production batch.

## 3. Minimal User schema additions

The first Stage 2 production batch will add only stable employee-profile data required for search and a genuine read-only profile:

### Search and identity support

- `previousNames`: normalized array of prior legal or recorded names.
- `employeeSearchTerms`: internal, generated, indexed search terms; excluded from normal responses.

### Employment summary

- `joiningDate`: optional date.
- `employmentType`: optional bounded text.
- `department`: optional bounded text.
- `designation`: optional bounded text.

### Private contact information

- `address`: optional structured subdocument.
- `emergencyContact`: optional structured subdocument.

The address fields are line 1, line 2, city, state, postal code and country.

The emergency-contact fields are name, relationship and phone.

The first batch will not add bank details, government identifiers, private HR notes, documents, profile-image storage, leave balances, shifts, tasks, loans or advances. Those require dedicated modules, storage or business rules and must not be invented inside `User`.

## 4. Normalisation rules

- `userId`, organisation and café identifiers remain uppercase.
- Email remains lowercase.
- Names are trimmed.
- `previousNames` are trimmed, empty entries removed and duplicates removed case-insensitively.
- Employment text fields are trimmed.
- Address and emergency-contact text fields are trimmed.
- Search terms are generated by the backend only.
- `employeeSearchTerms` must never be accepted from request bodies.

## 5. Indexed employee search design

Exact permanent User ID search will continue to use the existing organisation-and-user-ID unique index.

Name search will use `employeeSearchTerms`, generated from:

- legal name;
- preferred name;
- previous names.

The generated terms will contain normalized full values, words and bounded prefixes/substrings needed for case-insensitive partial matching. Search input will be normalized and compared using indexed equality rather than directly interpolated into an unescaped regular expression.

Add an index equivalent to:

```text
organisationId + employeeSearchTerms + accountStatus
```

The index must be named clearly and tested through `User.schema.indexes()`.

Search remains server-side and paginated. The browser must never receive the complete employee collection for local filtering.

## 6. Search result response contract

A search result may contain only:

```text
userId
name
preferredName
role
accountStatus
isPrimaryMaster
primaryCafeId
assignedCafeIds
joiningDate
department
designation
```

It must not contain:

```text
email
phone
address
emergencyContact
roleHistory
cafeAssignmentHistory
archiveReason
security timestamps
sessionVersion
permissionsVersion
password or MFA fields
employeeSearchTerms
```

Exact User ID matches will be prioritised before name matches.

## 7. Full employee profile response contract

The profile response will be assembled by an explicit backend response builder instead of returning the Mongoose User document directly.

### Common identity section

```text
userId
name
preferredName
previousNames where authorised
role
accountStatus
isPrimaryMaster
createdAt
updatedAt
```

### Employment section

```text
joiningDate
employmentType
department
designation
primaryCafeId
assignedCafeIds
```

### Contact section

```text
email
phone
address where authorised
emergencyContact where authorised
```

### History section

```text
roleHistory where authorised
cafeAssignmentHistory where authorised
archive lifecycle metadata where authorised
```

Unavailable Stage 2 modules will be omitted or represented through explicit availability metadata; fake records will never be generated.

Loans and advances now expose `SELF_SERVICE_INTEGRATED` availability only when the authenticated employee is viewing their own profile. This metadata does not authorize OWNER, CAFE_ADMIN, MASTER, or STAFF access to another employee's loan or salary-advance records.

## 8. Role and field visibility

### Master

May receive all Stage 2 employee-profile fields authorised by organisation scope. Primary Master protections continue to apply to mutations.

### Owner

Receives read-only identity, employment, café, contact and attendance information according to policy. Private address, emergency contact, private HR, bank, government-ID and security fields are excluded unless a later explicit policy allows them.

### Café Admin

May receive only employees currently intersecting the authenticated Admin's assigned cafés. The response is operational and excludes private address, emergency contact, histories not required for operations, payroll and security data.

### Staff

May receive only their own profile using `request.auth.userId`. Self-profile may include their own contact and private contact fields, but never security internals.

All record and field decisions are performed by the backend. Frontend role state is not an authority.

## 9. Sensitive and operational exclusions

Every employee read builder must exclude at minimum:

```text
passwordHash
passwordHistoryHashes
mfaSecretEncrypted
recoveryCodeHashes
failedLoginAttempts
lockedUntil
lastLoginAt
lastPasswordResetAt
passwordChangedAt
passwordExpiresAt
sessionVersion
permissionsVersion
mustChangePassword
employeeSearchTerms
```

The exclusion must remain effective even when a Mongoose document contains those fields.

## 10. Service boundary

Create a dedicated employee read service rather than expanding governance logic. The service will own:

- search-term normalization;
- generated employee search terms;
- record-scope filters;
- role-based search-result building;
- role-based full-profile building;
- security-field exclusion;
- pagination metadata helpers.

Stage 1 governance services remain responsible for role, status, café-assignment and Primary Master mutation protections.

## 11. First production batch

The next bounded implementation batch is:

1. Add schema subdocuments and the minimal profile fields.
2. Generate and normalize `previousNames` and `employeeSearchTerms`.
3. Add the employee-search index.
4. Create employee read-response builders.
5. Add direct unit tests for normalization, indexes and sensitive-field exclusion.
6. Run all backend tests and syntax validation.
7. Inspect the complete diff before committing.

The first batch will not alter routes, replace the Employees frontend, add attendance aggregation or expose salary information.

## 12. Required first-batch tests

- previous names are trimmed and deduplicated case-insensitively;
- search terms include legal, preferred and previous names;
- search terms are normalized and deduplicated;
- the employee-search index exists;
- search results contain only the approved compact fields;
- Master profile builder returns authorised profile fields;
- Owner response excludes private contact and security fields;
- Café Admin response excludes private contact, histories and security fields;
- Staff self-profile contains authorised own fields;
- all builders exclude password, MFA, session, permission and internal search fields;
- Primary Master validation and existing Stage 1 tests remain unchanged.

## 13. Boundary decision

The first schema batch is a read-foundation batch. Employee-profile mutation workflows, document storage, sensitive reveal/export, attendance summary integration and the API-backed frontend will follow in later bounded Stage 2 batches.
